# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 패턴이 십자가(Cross)인지 X인지 판별하는 Python 콘솔 프로그램입니다.
입력 패턴과 필터의 같은 위치 값끼리 곱한 뒤 모두 더해 점수를 구하고, 점수가 더 높은 필터로 판정합니다.

## 실행 방법

```bash
python main.py
```

실행하면 모드를 선택합니다.

- **1. 사용자 입력 (3x3)**: 필터 A, 필터 B, 패턴을 한 줄에 숫자 3개씩(공백 구분) 3줄 입력합니다.
- **2. data.json 분석**: `main.py`와 같은 폴더에 있는 `data.json`을 읽어 일괄 판정합니다.

## 개발 환경

- Python 3.8 이상 (개발: Python 3.14)
- 표준 라이브러리만 사용 (`json`, `time`), 외부 라이브러리 사용 안 함

## 구현 요약

### 라벨 정규화
data.json에는 같은 의미의 라벨이 여러 형태로 섞여 있습니다.
프로그램 내부에서는 표준 라벨 **Cross / X** 두 가지만 사용하도록 변환합니다.

| 원래 값 | 위치 | 표준 라벨 |
|---|---|---|
| `cross` | 필터 키 | Cross |
| `+` | expected | Cross |
| `x` | 필터 키, expected | X |

`normalize_label()` 함수가 앞뒤 공백 제거와 소문자 변환 후 변환표(`LABEL_MAP`)로 바꿉니다.

### MAC 연산
`mac()` 함수가 이중 for문으로 모든 칸을 돌며 `패턴[i][j] × 필터[i][j]`를 누적해 더합니다.
NumPy 같은 외부 라이브러리 없이 반복문으로 직접 구현했습니다.

### 동점 처리 정책 (epsilon)
소수 계산에는 미세한 오차가 생기므로 `==`나 `>`로 바로 비교하지 않습니다.
`abs(점수A - 점수B) < 1e-9` 이면 동점으로 보고 **UNDECIDED(판정 불가)** 로 처리합니다.

### 오류 처리
- 모드 1: 한 줄의 숫자 개수가 다르거나 숫자가 아닌 값이 있으면 안내 문구를 출력하고 그 줄을 다시 입력받습니다.
- 모드 2: 크기를 알 수 없는 키, 필터 누락, 알 수 없는 expected, 크기 불일치가 있으면 프로그램을 멈추지 않고 해당 케이스만 FAIL로 기록합니다.

## 결과 리포트

### 실행 결과 요약

- 총 테스트: 6개 / 통과: 3개 / 실패: 3개
- 실패 케이스: `size_5_1`, `size_13_2`, `size_25_1` (모두 동점 UNDECIDED)

### 실패 원인 분석

| 케이스 | Cross 점수 | X 점수 | 판정 | expected |
|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X |

실패 원인을 "데이터/스키마 문제, 로직 문제, 수치 비교 문제"로 나누어 점검했습니다.

1. **데이터/스키마 문제가 아닙니다.** 라벨 정규화로 `+`, `cross`, `x`가 모두 Cross/X로 바뀌었고, 6개 패턴 모두 필터와 크기가 일치해 크기 검사를 통과했습니다.
2. **MAC 로직 문제가 아닙니다.** 같은 코드로 나머지 3개 케이스는 정상 PASS했고, 모드 1에서 십자가 패턴 점수 5.0 / X 패턴 점수 1.0으로 손계산과 같은 값이 나왔습니다.
3. **수치 비교에서 두 점수가 사실상 같습니다.** 세 케이스 모두 두 점수 차이가 1e-16 수준으로, 수학적으로는 같은 값인데 부동소수점 오차로 끝자리만 다르게 계산된 것입니다.
4. 만약 epsilon 없이 `>`로 비교했다면 size_5_1은 Cross, size_13_2는 X, size_25_1은 Cross로 판정되어 **세 케이스 모두 오히려 틀린 답**이 나왔을 것입니다. 오차 때문에 생긴 우연한 차이로 판정하는 것은 신뢰할 수 없습니다.
5. 따라서 이 FAIL은 버그가 아니라, 주어진 필터로는 두 모양을 구별할 수 없는 패턴을 **동점 규칙에 따라 정직하게 판정 불가로 처리한 결과**입니다.
6. 개선하려면 비교 규칙을 바꾸기보다, 두 필터의 가중치를 다르게 설계해 점수 차이가 분명하게 나도록 필터를 조정해야 합니다.

### 시간 복잡도 분석

| 크기(N×N) | 평균 시간(ms, 10회) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.0009 | 9 |
| 5×5 | 0.0015 | 25 |
| 13×13 | 0.0070 | 169 |
| 25×25 | 0.0249 | 625 |

- MAC 연산은 N×N의 모든 칸에서 곱셈과 덧셈을 한 번씩 하므로 연산 횟수는 **N²** 이고, 시간 복잡도는 **O(N²)** 입니다.
- 13×13 → 25×25에서 연산 횟수는 약 3.7배(169 → 625), 측정 시간은 약 3.6배(0.0070 → 0.0249) 늘어 거의 같은 비율로 증가했습니다.
- 3×3 → 25×25는 연산 횟수가 약 69배인데 시간은 약 28배만 늘었습니다. 크기가 작을 때는 함수 호출과 반복문 준비 같은 고정 시간이 차지하는 비중이 크기 때문입니다.
- 즉 크기가 커질수록 측정 시간이 N²에 비례하는 모습에 가까워집니다.
- 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로, 이런 반복 연산을 동시에 처리하는 NPU 같은 전용 하드웨어가 필요합니다.
- 측정은 입력·출력·파일 읽기를 제외하고 `mac()` 함수 호출 구간만 10회 반복해 평균을 냈습니다.


## 추가 설명

### 라벨 확장 절차

새로운 라벨 표기나 새로운 모양을 추가할 때는 아래 순서로 진행합니다.

1. **새 표기 확인**: data.json에 기존에 없던 표기(예: `plus`, `X`, `cross ` 처럼 공백 포함)가 있는지 확인합니다.
2. **변환표 등록**: `LABEL_MAP`에 새 표기를 키로, 표준 라벨(Cross 또는 X)을 값으로 추가합니다. `normalize_label()`이 공백 제거와 소문자 변환을 먼저 하므로 키는 소문자로만 등록하면 됩니다.
3. **정규화 확인**: 모드 2를 실행해 필터 로드 메시지가 표준 라벨로 표시되는지, "알 수 없는 라벨" 경고가 나오지 않는지 확인합니다.
4. **판정 테스트**: 새 표기를 expected로 쓰는 케이스가 "알 수 없는 expected"로 FAIL 되지 않고 정상 판정되는지, 결과 요약의 PASS/FAIL 개수가 예상과 같은지 확인합니다.
5. **새 모양 추가 시(예: Circle)**: 표준 라벨을 하나 더 정하고, 크기별 필터에 해당 필터를 추가한 뒤, 판정을 "두 점수 비교"에서 "가장 높은 점수 선택 + 최고점 동점이면 UNDECIDED"로 확장해야 합니다.

### 모드별 동점 처리 정책

| 모드 | 동점일 때 화면 출력 | 집계 방식 | 이유 |
|---|---|---|---|
| 모드 1 (사용자 입력) | `판정 불가 (\|A-B\| < 1e-09)` | 집계 없음 | 정답이 없으므로 판정 불가 사실만 알려줌 |
| 모드 2 (data.json) | `UNDECIDED` | FAIL로 집계 | expected(정답)와 비교해야 하므로, 판정하지 못한 경우는 통과로 볼 수 없음 |

### epsilon 값과 시간 측정 방식의 근거

- **epsilon = 1e-9**: 이번 데이터의 부동소수점 오차는 1e-16 수준이고, 실제로 의미 있는 점수 차이는 0.1 이상입니다. 1e-9는 오차보다 충분히 크고 실제 차이보다 충분히 작아서 둘을 안정적으로 구분합니다. 반대로 epsilon을 너무 크게(예: 0.5) 잡으면 실제로 다른 점수까지 동점으로 처리되는 문제가 생깁니다.
- **time.perf_counter() 사용**: 짧은 구간을 재기 위한 고해상도 시계라서 마이크로초 수준의 MAC 연산 시간 측정에 적합합니다. 한 번 측정은 운영체제 상황에 따라 흔들리므로 10회 평균을 사용했습니다.
- **작은 N에서 비율이 낮은 이유**: 함수 호출, 반복문 준비, 시간 측정 자체에 드는 고정 시간(상수항)이 있어서, 연산 횟수가 적은 3×3에서는 이 고정 시간이 차지하는 비중이 큽니다. N이 커질수록 N²에 비례하는 부분이 커져 이론값에 가까워집니다.

### CPU와 NPU 비교 및 병목 지점

- **CPU(직렬 처리)**: 이 프로그램의 `mac()`은 25×25 패턴에서 625번의 곱셈을 **한 번에 하나씩 순서대로** 처리합니다. 크기가 커지거나 필터 수가 늘어나면 처리 시간이 그대로 늘어납니다.
- **NPU(병렬 처리)**: 수많은 MAC 연산 장치를 갖추고 있어 625번의 곱셈을 **동시에** 처리한 뒤 한꺼번에 더할 수 있습니다. 같은 일을 훨씬 짧은 시간에 끝낼 수 있습니다.
- **주요 병목 지점**
  - **메모리 대역폭**: 계산 장치가 아무리 빨라도 패턴과 필터 값을 메모리에서 가져오는 속도가 느리면 장치가 기다리게 됩니다.
  - **연산 유닛 포화**: 동시에 처리할 수 있는 MAC 장치 수보다 연산이 많으면 나머지는 차례를 기다려야 합니다.
  - **결과 합산(동기화)**: 각 장치가 계산한 곱셈 결과를 하나의 점수로 모으는 단계에서 서로 기다리는 시간이 생깁니다.
- **최적화 우선순위**: ① 불필요한 연산을 줄이는 알고리즘 개선 → ② 2차원 배열을 1차원으로 펴서 메모리 접근을 단순하게 하는 최적화 → ③ 여러 장치로 나누어 동시에 계산하는 병렬화 순서로 효과를 확인하는 것이 좋습니다.
